## 性能结果：旧预算未通过

六机位60帧测量完成，资源/控制台错误0。对仓库原 `tests/perf-p2.json` 的门禁仍失败：午门前 calls 188→211（+12.2%），乾清门159→178（+11.9%），均超过原10%阈值。没有重设基线或放宽阈值。V1按已知限制的结构预览交付，不是性能门禁通过版；下一轮优先合批材质，保留新增结构。

另外用同环境刚捕获的当前main作对照：

| 机位 | 当前main → V1 calls | calls变化 | 三角面变化 |
|---|---:|---:|---:|
| 午门前 | 194 → 211 | +8.76% | +3.71% |
| 太和殿前 | 171 → 181 | +5.85% | +3.92% |
| 乾清门 | 162 → 178 | +9.88% | +4.00% |
| 东六宫中 | 139 → 139 | +0.00% | -0.06% |
| 宁寿宫 | 121 → 121 | +0.00% | +0.02% |
| 御花园 | 154 → 154 | +0.00% | +0.06% |

相对新鲜main的calls最大增加9.88%、三角面最大增加4.00%，不能用这份补充对照掩盖原门禁失败。软件渲染fps受共享CPU影响，本轮不宣称桌面/手机帧率已达标。

冻结整合门禁最初仍使用30秒截图上限，因截图超时报回归失败；随后相同场景以120秒上限单独完整重跑24/24通过，原失败日志保留。这里使用的是最终各项证据，不宣称原先那次一键命令全绿。

截图快照与最终生产源的唯一区别为数据schema文档及PalaceBuilder方法注释，渲染/碰撞逻辑一致。

## 基线继承问题与测试修订

1. 神武门：主分支已移至 Z=542，锚点仍是531，偏差11 m，超过原5 m阈值。原值与阈值均保留，锚点检查仍失败；后续需要独立对齐城墙、城台、门楼的测量对象。
2. 原四门回归采样把神武门后端取到 Z=560 的世界边界，那里本来就应碰撞。只排除边界上的无效采样，仍覆盖门洞两侧与内部，其他三门采样数量不变；独立测试保护这一边界条件。未删除实际门墙碰撞断言。
3. 基线自动路线“武英门→浴德堂→返回”在60fps慢走时停于约(223.5,-244.1)，未达(246,-243.8)。基线151/152，初次整合155/156，均为同一故障；未改成忽略或降为警告。
4. 新中和殿南面围护与阶道具有真实碰撞。原来穿过窗口或阶侧栏墙的测试折线改走中央门/阶口；负向测试要求原穿越路径继续阻挡。交泰殿后门转弯也避开实体折叠门扇。
5. Chromium 软件渲染截图在共享环境里可能超过30秒；仅提高截图等待上限，不更改视口、渲染参数或断言。软件渲染fps不代表用户设备性能。
